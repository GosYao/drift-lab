Three Whys

The background in three questions, each answered with evidence from the lab.

Intent lives in more places than code. Terraform encodes what exists; it does not encode why this role may read only this table. That capability intent traditionally lives in review approvals, tribal memory, and runbooks. Anything not encoded somewhere checkable drifts silently.

This lab encodes it as policy-as-code: five Terraform test runs with mock providers asserting the support agent reads only customer-orders, identity pinning, workload hardening, and namespace isolation — verified in infra/workloads/policy.tftest.hcl, running credential-free in every PR.

Two reasons, both demonstrated here.

1. Generic rules, not your intent. The seeded support-role broadening — support-agent silently gaining read on customer-archive — passed the external Lacework IAC and SCA checks on the same PR where the intent-encoded gate failed it. One seeded case, recorded factually: compliance packs check industry rules; they do not carry your intent.

2. Noise. Raw plan output buries the two lines that matter under version fields, null-vs-empty churn, and IAM mirror updates. The sanitizer exists because triage cost is set by noise — and noise is a deterministic problem you can engineer away (changed-attribute paths, version filters, mirror collapse).

The expensive part was never detection; it is the human loop — connect finding, change, intent, fix, proof.

The demo's division of labor answers the objection: deterministic checks make the trust decision, and the agent does the correlation and explanation. The agent cannot override a gate, cannot fabricate evidence, and in this pipeline holds no credential that can touch anything: the review job has no GitHub token, and the posting job has no Factory key.

The trust model stays deterministic; the labor cost collapses — 57 seconds for the review job in the recorded run.

The metric: cost per verified fix

A fix counts as verified only when it passes deterministic re-verification — the agent's own review states the criterion. The recorded run gives the numerator's ingredients: 57 seconds of agent review, seconds of pinned scanners, zero cloud credentials.

The benchmark phase measures it properly across arms — scanners-only, plus ordinary Droid review, plus policy-as-code plus Droid — so the claim becomes a number instead of an anecdote. That phase is designed, not yet measured.

cost per verified fix = (scanner minutes + agent credits) ÷ fixes that pass deterministic re-verification

Honest boundaries

Stated on stage. They close objections; they are not fine print.

■
One seeded case. No generalization beyond it, no competitor-parity claims. The mechanism is the finding, not a leaderboard.
■
The UI is fixture replay. The local preview replays synthetic fixtures; live collection today is the CLI (python -m drift_lab collect). Wiring it into the UI is next.
■
The benchmark is designed, not yet measured. Cost per verified fix is the next phase's number, not today's claim.
■
No automatic reconciliation. Drift is detected and explained; remediation stays authorized human work.
■
The agent never holds trust. A model may explain evidence; it cannot fabricate graph edges or make the trusted validation decision. That decision stays with the deterministic gates.
Detection is solved — we proved it by making our own gate catch what the vendor scanners passed. What is not solved is turning findings into decisions, and decisions into verified fixes. That is the 57 seconds you just saw — and it is why the next phase measures cost per verified fix.
